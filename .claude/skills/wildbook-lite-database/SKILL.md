# wildbook-lite Database Skill

Companion to `wildbook-lite-dev`. This skill describes the Postgres
schema that JPA/Hibernate generates from the entities, the FK web that
makes cascade deletes order-sensitive, and useful SQL recipes for
investigating data without booting the app.

## Schema Source of Truth

There is no hand-managed `.sql` migration today. The schema is
generated by Hibernate via `spring.jpa.hibernate.ddl-auto: update` on
startup. Entity classes are the source of truth. Flyway is on the
classpath, **not yet wired into the migration flow** — when this
project moves toward production, the path is "freeze the current
schema as `V1__init.sql`, switch ddl-auto to `validate`, every change
goes through a Flyway migration".

Convention for column naming:
- `snake_case` columns mapped from `camelCase` Java fields.
- `@Column(name = "...")` is used when Hibernate's default differs from what we want.
- Foreign keys are always `<entity>_id` (e.g., `project_id`, `encounter_id`).
- Booleans are `boolean` (or `is_*`) — we never use `tinyint(1)`.
- Timestamps are `timestamp` (TIMESTAMP WITHOUT TIME ZONE) mapping to `LocalDateTime`.

## Operational Safety (Dev Database)

Even though this is a learning project, treat the local DB with care:

1. **Wrap multi-row mutations in `BEGIN; ... COMMIT;`.** Verify the SELECT count before committing.
2. **`ddl-auto: update`** can ADD columns/tables but won't DROP them — old columns linger after a refactor. Use `psql -d wildbook_lite -c '\d encounter'` to see what's actually there.
3. **Drop-and-recreate is fine** for total schema resets: `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` then restart the app.
4. **Don't `TRUNCATE` parents** of FK-protected children — Postgres will refuse. Use `TRUNCATE … CASCADE` or delete children first.

## Foreign Key Map

```
users
 ├─< refresh_token (user_id)
 ├─< project_member (user_id)
 └─< notification (user_id)

project
 ├─< project_member (project_id)
 ├─< encounter (project_id)         -- soft FK (just a Long, no JPA navigation)
 └─< occurrence (project_id)        -- soft FK

occurrence
 └─< encounter (occurrence_id)

individual
 └─< encounter (individual_id)
 └─< match_candidate (individual_id)

observer
 └─< encounter (observer_id)
 └─< sighting (observer_id)

taxonomy
 └─< encounter (taxonomy_id)

encounter
 ├─< sighting (encounter_id)
 ├─< comment (encounter_id)
 ├─< media_asset (encounter_id)
 ├─< encounter_tag (encounter_id)
 ├─< encounter_status_history (encounter_id)
 └─< annotation (encounter_id)
                 ├─< feature (annotation_id)
                 │           └─> media_asset  (feature.media_asset_id → media_asset.id)
                 └─< ia_task (annotation_id)
                              └─< match_result (ia_task_id)
                                              └─< match_candidate (match_result_id)
```

Notes on the "soft FK" rows:
- `encounter.project_id`, `encounter.submitter_user_id`,
  `encounter.assigned_to_user_id`, `occurrence.project_id`,
  `occurrence.submitter_user_id`, `notification.user_id` are stored as
  bigint columns WITHOUT JPA relations. They behave like FKs from a
  schema-correctness perspective but Hibernate won't enforce them
  unless we add explicit FK constraints. Today we don't. **A junior
  reading this should not assume a `JOIN users ON users.id =
  encounter.submitter_user_id` is index-backed** — there's no
  Hibernate-generated index. Add one if you write a query that needs
  it.

## Cascade-Delete Order (Encounter)

`EncounterService.deleteById(id)` runs these `@Modifying` bulk deletes
in this exact order, then flushes, then deletes the parent:

```
1. feature.delete    where annotation in (… where encounter_id = :id)
2. annotation.delete where encounter_id = :id
3. sighting.delete   where encounter_id = :id
4. comment.delete    where encounter_id = :id
5. media_asset.delete where encounter_id = :id
6. encounter_tag.delete  where encounter_id = :id
7. encounter_status_history.delete where encounter_id = :id
8. encRepo.flush()                  -- forces all bulk DELETEs to land
9. encRepo.delete(encounter)        -- finally drops the parent row
```

**Why the flush** — Hibernate's auto-flush may schedule the parent
DELETE before the bulk children when both are queued, which trips an
FK violation in Postgres. The explicit flush forces the bulk statements
out first.

**Why feature before annotation** — `feature.annotation_id` references
`annotation.id`. Drop the bridges before their parent annotation rows.

**What's NOT in the cascade**:
- `ia_task` (and its `match_result` + `match_candidate`) — these tie to
  `annotation_id`, so they get orphaned if the annotation goes away.
  This is a known gap. If you need IA tasks to die with the encounter,
  add a bulk delete `where annotation in (... encounter_id = :id)` ahead
  of step 2 here. Today they linger in the DB with a dangling FK.
- `audit_log` — never cascade. Audit history must survive entity deletion.
- `notification` — independent of encounter delete; cleanup job sweeps later.

## State Machine Lookup

The encounter workflow lives in `encounter/EncounterStatus.java`:

```sql
SELECT id, status FROM encounter WHERE project_id = ? ORDER BY id;
-- Possible values (stored as STRING, NOT ORDINAL):
--   DRAFT      (initial)
--   REVIEWED   (EDITOR+ promoted from DRAFT)
--   PUBLISHED  (OWNER promoted from REVIEWED)
--   ARCHIVED   (OWNER promoted from PUBLISHED)
-- Plus reopen arrows back to DRAFT (OWNER only).
```

IA task lifecycle (`ml/IaTaskStatus.java`):

```
PENDING → RUNNING → DONE | FAILED
PENDING → CANCELLED (user-initiated only)
```

## Common Queries

### "What encounters does this project have, by status?"

```sql
SELECT status, COUNT(*) AS n
FROM encounter
WHERE project_id = $1
GROUP BY status
ORDER BY status;
```

### "Where's the workflow timeline for one encounter?"

```sql
SELECT id, from_status, to_status, user_id, created_at, message
FROM encounter_status_history
WHERE encounter_id = $1
ORDER BY created_at ASC;
```

### "Find encounters in a hierarchical region"

```sql
-- location_id is "USA/CA/Monterey Bay" — prefix match
SELECT id, species, encounter_date, location_id
FROM encounter
WHERE project_id = $1
  AND location_id LIKE 'USA/CA/%'
ORDER BY encounter_date DESC
LIMIT 100;
```

### "Top species in a project"

```sql
-- Uses the denormalized species column for speed.
-- For canonical names join taxonomy:
SELECT
  COALESCE(t.scientific_name, e.species) AS species,
  COUNT(*) AS n
FROM encounter e
LEFT JOIN taxonomy t ON t.id = e.taxonomy_id
WHERE e.project_id = $1
  AND e.status = 'PUBLISHED'
GROUP BY 1
ORDER BY n DESC
LIMIT 10;
```

### "What's pending in the ML queue right now?"

```sql
SELECT id, annotation_id, status, created_at, started_at
FROM ia_task
WHERE status IN ('PENDING', 'RUNNING')
ORDER BY created_at ASC;
```

### "Best matches for a given annotation across all IA runs"

```sql
SELECT
  i.id   AS task_id,
  mc.individual_id,
  ind.nickname,
  mc.score,
  mc.rank_position,
  i.created_at
FROM ia_task i
JOIN match_result mr  ON mr.ia_task_id = i.id
JOIN match_candidate mc ON mc.match_result_id = mr.id
JOIN individual ind   ON ind.id = mc.individual_id
WHERE i.annotation_id = $1
  AND i.status = 'DONE'
ORDER BY i.created_at DESC, mc.rank_position ASC;
```

### "Orphan sightings ready to be reported"

```sql
SELECT id, observer_id, sighting_date, location
FROM sighting
WHERE encounter_id IS NULL
ORDER BY sighting_date DESC;
```

### "Annotations of an encounter with their image links"

```sql
SELECT
  a.id           AS annotation_id,
  a.species,
  a.viewpoint,
  a.is_exemplar,
  f.id           AS feature_id,
  f.type         AS feature_type,
  m.id           AS media_asset_id,
  m.file_name,
  m.file_path
FROM annotation a
LEFT JOIN feature  f ON f.annotation_id = a.id
LEFT JOIN media_asset m ON m.id = f.media_asset_id
WHERE a.encounter_id = $1
ORDER BY a.id, f.id;
```

### "Audit trail for a user's last 50 actions"

```sql
SELECT id, action, user_id, target_id, status, latency_ms, created_at
FROM audit_log
WHERE user_id = $1
ORDER BY created_at DESC
LIMIT 50;
```

### "Find encounters whose denormalized species drifted from taxonomy"

```sql
-- Should always return 0 rows. If not, something bypassed
-- EncounterService.update() — e.g., a direct repo.save in a test.
SELECT e.id, e.species AS denorm, t.scientific_name AS canonical
FROM encounter e
JOIN taxonomy t ON t.id = e.taxonomy_id
WHERE e.species IS DISTINCT FROM t.scientific_name;
```

## Gotchas

### 1. `@Enumerated(STRING)`, never ORDINAL

Every enum column in this schema stores the **name**. Reordering an
enum constant is safe. If you ever see a row with an integer for an
enum, that's a bug — find it and rewrite the column.

### 2. `version` columns are silent

`@Version` adds a `version` bigint column. Concurrent updates to the
same row throw `OptimisticLockingFailureException` (Spring) /
`StaleObjectStateException` (Hibernate). It's surfaced as HTTP 409 by
the global exception handler. If clients see 409 unexpectedly, they
either:
- have a stale entity (refetch + retry), OR
- are doing parallel updates that should be a single transaction
  upstream.

### 3. `denormalized species` ↔ `taxonomy.scientific_name`

Reads use `encounter.species`. Writes go through
`EncounterService.update()` which syncs both. A direct `UPDATE encounter
SET taxonomy_id = X` outside the service WILL drift the denorm. Use the
check query above to catch.

### 4. Soft FKs aren't indexed by default

`encounter.submitter_user_id` and friends are `bigint` columns with no
Hibernate-generated index. If you start filtering by them in a list
query, add an explicit `@Index` to the entity (and re-run with
`ddl-auto: update`).

### 5. `dynamic_properties` is opaque to SQL

It's a text column holding a JSON string. Queries on its contents
require either:
- Cast inside the query: `dynamic_properties::jsonb ->> 'key'`, OR
- Migrate the column to `jsonb` (one-line `ALTER TABLE`) when we hit
  enough usage to need indexed JSON queries.

### 6. Soft-deleted users still own rows

`users.deleted_at IS NOT NULL` means the user is "gone" from the auth
perspective. But every `encounter.submitter_user_id` they ever set is
still there pointing at the dead row. Filter user listings on
`deleted_at IS NULL`. Don't filter encounter listings — the historical
attribution still matters.

### 7. `audit_log` writes survive parent rollback

The audit aspect uses `Propagation.REQUIRES_NEW`. So you might see an
`audit_log` row for an operation that visibly failed — that's expected
("we attempted X, then it errored"). Look at `audit_log.status` to
distinguish OK from FAIL.

### 8. OpenSearch is eventually consistent

The OS index lags Postgres by however long it takes the
`@TransactionalEventListener(AFTER_COMMIT) + @Async` chain to flush.
If you query the OS endpoint right after a write, you may see the old
state. For exact correctness, use the Postgres FTS endpoint instead.

## Useful psql shortcuts

```sh
# Schema for a table
psql -d wildbook_lite -c '\d+ encounter'

# Foreign keys touching a table (both directions)
psql -d wildbook_lite -c "
  SELECT conname, pg_get_constraintdef(oid)
  FROM pg_constraint
  WHERE contype = 'f' AND (conrelid = 'encounter'::regclass OR confrelid = 'encounter'::regclass);
"

# Approximate row counts (cheap — uses stats, not COUNT(*))
psql -d wildbook_lite -c "
  SELECT relname, n_live_tup
  FROM pg_stat_user_tables
  ORDER BY n_live_tup DESC;
"

# Index usage stats — find unused indexes
psql -d wildbook_lite -c "
  SELECT relname, indexrelname, idx_scan, idx_tup_read
  FROM pg_stat_user_indexes
  ORDER BY idx_scan ASC;
"

# What's blocking what right now
psql -d wildbook_lite -c "
  SELECT pid, usename, state, wait_event_type, wait_event, query
  FROM pg_stat_activity
  WHERE state != 'idle';
"
```

## When You Plan a Schema Change

1. Update the entity class (`@Column`, `@Index`, `@Enumerated`, etc.).
2. Restart the app once with `ddl-auto: update` and inspect via `\d` that
   the column landed as expected.
3. If you're DROPPING a column, do it manually — `update` won't.
4. When this project moves toward production, freeze current schema as
   `V1__init.sql`, switch to `ddl-auto: validate`, and start writing
   real migration files (`V2__add_xxx.sql`).
